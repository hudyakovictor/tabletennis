# Table Tennis WTF: Единая Визуальная Мастерская

## Цель

Создать в исходниках постоянную desktop-мастерскую UI-kit для всей mobile-first Telegram Mini App. Она показывает настоящие компоненты, полные мобильные экраны, игровые ассеты и интерактивные сцены; позволяет изменять оформление и сохранять настройки в проект. `python3 source/build.py` компилирует эти же исходники и сохранённые настройки в `play/index.html`.

Ориентир: выразительность и завершённость интерфейса премиальной игры, не технический прототип. 99/100 по 65 факторам ниже является целевым уровнем, а не уже полученной оценкой. UI-kit сам по себе не обеспечивает качество физики, сетевой инфраструктуры или награду «Игра года».

## Зафиксированные Решения

- Один авторский источник полного представления: `source/src/ui-kit/`. Здесь разметка, композиции, CSS, иконки, иллюстрации, визуальные модели/материалы, состояния, переходы, эффекты и их настройки. Один источник не означает один большой файл или один объект на все экземпляры.
- Страницы становятся контроллерами: выбирают именованный `View`, передают данные и действия, подписываются на сервисы. Ни HTML, ни CSS, ни рисования/изменения DOM, ни собственного визуального поведения в страницах. Уникальный блок также регистрируется в библиотеке.
- Сохранить vanilla JS/CSS/WAAPI и существующую Python-сборку. Не вводить React, второй игровой рендерер или универсальный редактор приложений.
- Художественная основа заменена по пользовательскому референсу `image-1 (1).png` от 2026-11-06: тёмная неоновая спортивная арена, midnight/navy поверхности, тонкие светящиеся cyan-контуры, синие объёмные кнопки с белыми надписями, красное главное действие, золотые награды и оригинальный graffiti-логотип WTF. Белые наклонные спортивные заголовки, подсветка предметов и металлическая отделка вместо молочных бумажных карточек, асфальтового минимализма и индустриальных наклеек. Референс определяет оформление, не подтверждает реализацию показанных на нём онлайн-сервисов.
- Цвет действия (`primary`), золотой цвет наград (`accent`) и цвет контура (`edge`) независимы в редакторе. Настройка синей кнопки не перекрашивает валюту или канонический `STROKES`; игровые и мастерские компоненты используют общие градиенты/материалы.
- Мастерская содержит UI всей будущей игры, включая онлайн и турниры. Их ещё не реализованные сервисы заменяются только в мастерской явно обозначенными сценариями. Не добавлять фиктивный онлайн, оплату или выдачу призов в игровую сборку.
- Текущие работающие интерфейсы подключаются к библиотеке поэтапно. Не переписывать физику, правила, распознавание, экономику и серверную часть ради переноса UI.
- Не менять ID предметов, сейв v10, полученные награды, экипировку, историю, сроки сундуков и цены. Сохранить идемпотентность и обработку ошибки записи.
- Сохранить одну настоящую 3D-сцену, в том числе мобильное лобби бот-бот без персонажей. Цвета техник/контакта/следа задаёт канонический `STROKES`, не произвольная тема магазина.
- Сохранить согласованный сценарий прелоадера: ракетки без персонажей, два оборота, немедленный полёт вправо, передача управления настоящей сцене. Меняется оформление, не этот контракт.
- Все существующие незакоммиченные изменения и пользовательские оригиналы сохранить. Никаких автоматических коммитов, откатов, публикаций или новых Agent Manager sessions.

## Текущее Основание

- `source/build.py` собирает оболочку и вызывает `source/game/tt/build.py`, встраивая движок в iframe. Общие токены уже подключаются к обоим документам, но разметка, параметры и эффекты остаются распределёнными.
- Общий CSS оболочки перенесён из `css/base.css` в зарегистрированный `ui-kit/components/shell.css`; кнопки, панели и навигация используют материалы из `ui-kit/components/materials.css`. Пять существующих эталонов перерабатываются в Neon Arena; это не объявление готовности остальных 23 групп.
- `core/ui_core.js` содержит одновременно Router и визуальные реализации Sheet, Nav, toast и переходов. Их нельзя оставить обходным путём мимо новой библиотеки.
- Разметка есть также в сервисах наград/диагностики, `priceTag` в `data/catalog.js`, `index.tpl.html`, прелоадере и видимых панелях движка. Проверять только `screens/` недостаточно.
- Рабочие контракты `UI.own/dispose`, возврата в родительский слой, repaint без повторной выдачи, locale refresh и восстановления сессии сохраняются. Не создавать рядом второй независимый механизм владения.
- Образец экземплярного API уже есть в `ui/match_hud.js`: `MatchHUD.mount` с update/dispose, локальным состоянием и защитой событий. `UI.own` сейчас группирует по ближайшим screen/sheet, поэтому дополнить его дочерними scopes, а не считать достаточным для произвольных вложенных компонентов. `ui/fx.js` и `Wallet.show` пока используют глобальные canvas/селекторы; их необходимо отвязать от singleton-экрана.
- Нельзя открыть существующий `Router` в 28 iframe и назвать это безопасной витриной: `match.render` выбирает launch, result может начислять награды, chest/уведомления выполняют reconcile, hub/Academy обращаются к живому `GameHost`. Сначала отделить чистые presentation-модели.
- Вынести также цвета и параметры из `css/match_hud.css`, SVG в `screens/training.js`, JS в `ui/bg.js`/`ui/fx.js` и локальных переопределений Академии. Наличие `tokens.css` сейчас не означает отсутствие собственных палитр.
- Аналогично нельзя использовать старый engine workshop как новый UI-kit: `80_ui.js` привязывает глобальный DOM, аналитику, покупки, сохранение training progress и показ наград. Разделить его на визуальные компоненты и engine adapters; не переносить побочные эффекты в каталог.
- До изменений снять текущий baseline и сопоставить визуальные решения с `6e6f942` без отката рабочего дерева. Старый код является справочным материалом, не заменой текущих исправлений.

## Источники И Сборка

Предлагаемая структура, без генерации копий страниц в `source/`:

```text
source/src/ui-kit/
  manifest.json          # имена, зависимости, targets, ресурсы, варианты, сценарии
  theme.json             # единственная активная сохранённая конфигурация
  theme.schema.json      # типы, диапазоны и описание редакторских контролов
  runtime/               # реестр, экземпляры, lifecycle, слои и motion
  components/            # Button, Text, Field, Card, Tabs, Sheet и т. п.
  blocks/                # ShopItem, RewardSummary, ContactMap, GestureDiagram
  views/                 # полные представления всех экранов
  effects/               # ChestReveal, CoinFlight, Intro, Victory, LevelUp
  assets/                # канонические визуальные ресурсы и их реестр
  workshop/              # исходники мастерской, fixtures, каталог состояний
source/tools/ui_kit.py    # локальный запуск мастерской и безопасное сохранение
source/ui_kit_build.py    # общий компилятор конфигурации/manifest для обоих build
build/ui-kit/            # генерируемая витрина и результаты проверок, не production
play/index.html          # единственный игровой HTML
```

Поток: редакторский draft -> проверка -> запись `theme.json` -> единый snapshot сборки -> runtime CSS/параметры/модули/ресурсы -> оболочка и iframe движка.

- Старый `tokens.css` перестаёт быть независимо редактируемым источником. Из конфигурации генерировать CSS и JS-параметры в build context, а не сохранять вторую ручную тему.
- `manifest.json` определяет явный граф зависимостей и targets `shell`, `engine`, `workshop`. Отсутствующие имена/файлы, циклы и несовместимые зависимости останавливают сборку, а не молча пропускаются.
- Оба сборщика используют общий компилятор. Полная сборка передаёт движку тот же snapshot конфигурации; не перечитывать изменяющийся файл независимо посередине сборки.
- Записывать общий content hash визуальной конфигурации в оболочку, iframe и витрину. Отдельно сохранять fingerprints их target-модулей. Сохранение во время сборки не должно создавать смесь двух ревизий.
- Standalone `build/engine.html` использует тот же источник, без копий темы/картинок в дереве движка. Факт двух изолированных JS-контекстов не считается двумя авторскими реализациями.
- Перевести `source/tests/shell-fixture.cjs`, `source/game/tests/helpers.cjs`, проверки freshness и i18n на новые пути/manifest. Fixtures и сборка должны включать одинаковые зависимости, без второго ручного списка компонентов и пропуска нового CSS.
- В production включать только зависимости работающих маршрутов и нужные варианты ресурсов. Editor, fixtures, сценарии будущих сервисов и файловый API исключать из графа поставки, а не просто скрывать CSS.
- Сохранить текущий бюджет `4_963_084 + 1_048_576` байт для игрового HTML. Отчёт по модулям/ресурсам обязателен; увеличение бюджета требует отдельного решения, не маскируется удалением оформления.

## Контракт Компонентов

Минимальный реестр поверх существующего lifecycle, не новый большой фреймворк:

```js
const view = UIKit.mount('ResultView', host, props, environment);
view.update(nextProps);
view.dispose();
```

- Представления используют именованные базовые элементы, блоки, layouts и эффекты. Никаких `customHtml`, произвольных CSS/className/style, render-функций или callbacks с доступом к DOM как лазейки. Slots содержат только описания зарегистрированных компонентов; наружные события передают данные, не DOM-узлы.
- API описывает допустимые свойства, варианты, события и ресурсы. Данные безопасно экранируются; строки локализации и ID предметов остаются каноническими.
- Компонент владеет своим DOM, временным UI-состоянием, событиями и анимациями. Не импортирует `S`, кошелёк, сеть или `GameHost`. Игровые действия уходят наружу через явные callbacks.
- Environment предоставляет ограниченные clock/RNG, locale, motion, audio/haptic и scene ports. Эффекты не используют RNG матча. Workshop и production реализуют порты по-разному, но рендерят один код.
- Каждый экземпляр получает независимый scope/ID, уникальные SVG-defs и cleanup. Обновление данных/языка не повторяет FX, не теряет фокус/прокрутку и не дублирует обработчики.
- Router repaint/locale update уничтожает только представление; leave завершает игровую сессию по прежним правилам. Выбор соперника, launch ID, reconcile и отправка Progress не допускаются в render/update и не повторяются при смене темы.
- Прелоадер принадлежит `AppShell`, а не уходящему splash View: он запускает hub до конца полёта. Сохранить requestId-bound `lobbyReady/lobbyFrame`, завершение с удержанием готовой сцены и явную отмену при уходе из hub. Универсальный route-dispose не должен обрывать handoff.
- Покупка или награда сначала подтверждается доменным сервисом, затем компонент получает неизменяемый результат/receipt. Skip, Back, unmount и повторный render не влияют на начисление.
- Сохранить недекоративные guards в адаптерах: replay привязан к match token и тому же iframe, не к сохранённому отчёту; Academy-команды несут request/session/attempt/phaseToken/phase. Preview запрещён во время check, завершение справки возвращает её владельца, а не делает blanket resume.
- Перенести технические wrappers/порталы в `AppShell` и общий runtime. Вне библиотеки допустимы лишь bootstrap/mount adapters и настоящий игровой рендерер, не авторские оформления.
- Добавить dev-only AST-проверку JS на Acorn и проверку CSS/manifest: запрещать DOM/CSS/рисование в контроллерах и доменных сервисах, прямые зависимости компонентов от доменных singleton, незарегистрированные визуальные модули и ресурсы. Parser/lockfile являются build dependencies, не частью игрового JS. Не полагаться только на regex; запретить также обход через eval/динамическую загрузку визуального кода.
- На время миграции разрешить только точечный список уже существующих нарушений. Он может уменьшаться, но не легализовать новые. Финальный список пуст; широкие исключения для всех `services/` или `engine/` запрещены. В техническом рендерере разрешена геометрия/рисование мира, но не вторая UI-тема.

## Панель Настроек

- Общие роли и component variants: фон/поверхности/текст/акценты/статусы, границы, материалы и тени, радиусы, типографика, размеры контролов/иконок, spacing/density, motion и responsive-параметры.
- Разделять системный токен, его наследование и зарегистрированное переопределение варианта. Страница не может создать своё переопределение. Показывать, какие компоненты и экраны зависят от выбранного параметра.
- Шрифты выбирать из включённого реестра с RU/EN-глифами; не добавлять внешнюю загрузку шрифтов. Редактор не меняет физические размеры зоны контакта, пороги распознавания, баланс или стоимость предмета.
- Live preview во всех затронутых экземплярах, изменение одного компонента/варианта, сравнение сохранённого и draft, Undo/Redo, сброс секции, presets и явные состояния «Не сохранено / Сохранено / Ошибка / Конфликт».
- Редактор меняет зарегистрированные параметры, не генерирует произвольный JS/CSS и не заменяет инструменты создания моделей/иллюстраций. Новый тип компонента создаётся кодом в библиотеке и регистрируется вместе со сценарием и редактируемыми параметрами.
- Цвет, запечённый в растровую иллюстрацию, не становится CSS-токеном автоматически. Для него предусмотрен выбор зарегистрированного ресурса/варианта; для 3D-материалов параметры передаются рендереру явно. Inspector показывает, что наследуется от темы, а что является авторским ассетом.
- Локальный сервер слушает только loopback. Запись через защищённый JSON POST с проверкой Origin/Host и сессионным токеном; адрес файла не принимается от клиента. Ограничить размер, неизвестные ключи, значения, path traversal и симлинки за разрешённую область. Не использовать wildcard CORS или выполнение переданного кода.
- `Save` записывает только разрешённую конфигурацию после валидации; временный файл и atomic replace, сравнение ожидаемой ревизии. Вторая вкладка/внешняя правка не затирается: показать конфликт и предложить загрузить актуальные значения. Ошибка диска сохраняет draft и старый корректный файл.
- Browser storage допустим только для несохранённого черновика/раскладки мастерской, не как источник production-сборки. Git остаётся историей проекта; Save не делает commit.
- Предусмотреть одну команду локального запуска `python3 source/tools/ui_kit.py serve`; текущую команду игровой сборки сохранить. Архитектурная проверка запускается и отдельно через `npm run check:ui-kit` из `source`, и как обязательный этап build.

## Устройство Мастерской

- Desktop 1920x1080: каталог слева, рабочая доска в центре, инспектор справа. Это рабочий инструмент с высокой информационной плотностью, а не растянутое мобильное меню.
- Разделы: «Все экраны», «Элементы», «Блоки», «Ассеты», «Сцены и эффекты», «Тема», «Проверки». Поиск по имени/ID, связи «где используется», фильтр состояния готовности.
- Все мобильные экраны находятся на одной масштабируемой доске. Обзорные миниатюры, pan/zoom, раскрытие 1:1, варианты 320/360/390/430 px, планшет/desktop, RU/EN, safe-area и клавиатура. Не обещать вместить все страницы в 1920x1080 в натуральном масштабе.
- Карточка preview задаётся `{viewId, scenarioId, viewport, locale, themeRevision}`. Она использует тот же View и полный набор компонентов, а не отдельную HTML-имитацию.
- Изолировать документы preview и UI-контекст. Не запускать production boot, настоящий store, Telegram SDK, API, платежи или сетевые комнаты. Мокируются данные и внешние действия, а не изображения компонентов.
- Задавать настоящий viewport документа preview: узкий div внутри desktop не воспроизводит `dvh`, viewport media queries и safe-area. Масштабировать внешнее представление кадра, не подменять внутреннюю геометрию мобильного интерфейса; проверку ввода выполнять в 1:1.
- Контролируемый протокол parent/preview проверяет source window, instance ID, revision и тип сообщения. Preview не имеет доступа к файловому API и реальным сейвам; внешние соединения запрещены политикой preview.
- Виртуализировать большую доску. Одновременно работает один тяжёлый 3D-preview выбранной сцены; остальные показывают явно обозначенный кадр, полученный тем же движком. При изменении темы кадры инвалидируются/обновляются. Не подменять настоящий игровой рендер вторым 2D-движком.
- Для FX: запуск, повтор, пауза, scrub и контрольные фазы, скорость просмотра, обычный/reduced motion, качество, звук по явному включению. Таймлайн FX не управляет игровым временем или RNG.

## Охват Экранов

Manifest должен содержать все 28 групп ранее описанного продукта, включая вложенные панели:

| Группы | Представления |
| --- | --- |
| 1-7 | Загрузка/первый вход; главная; бот; онлайн/подбор; комната друга; перед матчем; игровой HUD |
| 8-14 | Пауза/помощь; итог; разбор; повторы; Академия; карточка урока; учебная сессия |
| 15-21 | Свободная тренировка; магазин; товар/покупка; карьера; коллекция; достижения; лиги/рейтинг |
| 22-28 | Сезон; список турниров; карточка/сетка турнира; задания/подарки/очередь; сундук/награды/level-up; уведомления; настройки/служебные состояния |

Для каждого View зарегистрировать применимые default/empty/loading/error/disabled/owned/claimed/full/long-content и состояние возврата. Для онлайн: idle/search/cancel/found/ready/disconnect/reconnect/timeout/peer-left/result. Для турнира: registration/full/closed/check-in/waiting/active/eliminated/finished/cancelled, сетка и переходы раундов. ## Ассеты И Сцены

- Один визуальный asset ID на запись: источник, права/происхождение, варианты разрешения, прозрачность, размеры и зависимости. Исходные тяжёлые материалы можно хранить отдельно от включаемых runtime-вариантов; не встраивать все masters в HTML.
- Отличать товарную иллюстрацию от texture/material: текущие `shop_*.webp` являются изображениями освещённых предметов, а не готовыми текстурами поверхности ракетки. Валидировать alpha/mask, crop/pivot и все обязательные ссылки. Правдоподобный fallback не должен скрывать отсутствующий ресурс в релизной сборке.
- Существующие товары связываются с asset IDs без переименования товарных IDs. Геометрия/материалы ракетки, магазинное превью, иконка и скин являются представлениями одной записи, а не независимыми предметами.
- Учесть текущий мост `92_embed.js`: `b-ink -> b_carb`, `r-coral -> r_tops`, `r-void -> r_hyb`, `r-teal -> r_ctl`. Ownership/цены остаются в shell catalog, характеристики в engine `84_racket.js`/versioned descriptor; визуальный manifest не копирует эти данные. Поддержанные сейчас типы: rubber/blade/table; trail/frame и новые будущие скины не становятся продаваемыми от одного наличия арта.
- Не редактировать `SHOP[].col` через тему: `Catalog.rewardItem` использует этот цвет для декодирования старых наград. Завести отдельный visual `displayColor`/material reference по стабильному item ID; сохранить исходную совместимость наград.
- `ItemArt.card` сейчас читает `S`, Catalog и цену. Разделить его на построение view model вне UI-kit и чистую карточку в библиотеке; простое перемещение исходного файла не обеспечивает изоляцию.
- Игровой рендер и `RacketPreview` потребляют одну визуальную спецификацию. Проверять соответствие видимой поверхности реальной контактной геометрии; не править физику из панели оформления.
- Текущий контур из `60_scene.js` связан с расчётом clearance в `38_paddle_motion.js`. Сохранить его как канонический meshRef. Произвольный редактор формы, меняющий габариты/контакт, вне этого UI-проекта; новый физически значимый контур требует отдельной валидации, не косметического слайдера.
- Устранить реальное расхождение preview: `66_training_preview.js` сейчас рисует PaddleRig без экипированных материалов, тогда как `70_game.js` их разрешает. Выделить один resolver внешнего вида, использовать в обоих местах; включить theme/material revision в cache key и освобождать заменённые ресурсы. Иначе сохранённые настройки не будут видны в 3D до перезапуска/смены item ID.
- Иллюстрации техник, стрелки, схемы, курсор и жестовые дорожки централизовать. Дорожка строится по каноническому recipe/геометрии input canvas; изменение размера карточки не изменяет длину/темп требуемого жеста.
- Сохранить действующие каталоги/descriptor и FSM Академии как источники правил. Выносить представление, а не создавать второй список техник, параметры ракетки или критерии зачёта.
- Сохранить различие `TrainingPreview` между `semantics: 'flight'` и `inputReplay: false`: 3D-полёт сам по себе не доказывает правильность показанного свайпа. В витрине раздельно показывать демонстрацию жеста, репетицию ввода и физическое превью полёта.
- `ChestReveal`, `CoinFlight`, `MatchIntro`, `Victory`, `Defeat`, `LevelUp`, preloader являются именованными полноценными сценами. Для каждой: состояния, anchors, cancellation, replay, reduced motion и явный конечный кадр с доступными действиями.

- Текущий logo имеет исходные 225x372 px; 22 картинки техник получены вырезанием мелких фрагментов листа на canvas 224x224, не созданием новых высокодетальных masters. Проверить реальное качество в целевых размерах/DPR; при необходимости подготовить новые согласованные ресурсы. Простое увеличение canvas или апскейл не считается художественной доводкой.

7. **Финальная приёмка.** Проверить всю матрицу, видео эффектов, реальные устройства, производительность, source-save/build roundtrip и отсутствие editor/demo в production. Выпустить только собранный `play/index.html`; отчёт разделяет выполненное, непроверенное и заблокированное.

## Проверки И Выпуск

- Unit: compiler/schema, циклы/неизвестные имена, escaping, targets, конфликт/ошибка Save, один snapshot обоим сборщикам. Неизвестные свойства не игнорируются.
- Architecture: отрицательные fixtures с DOM/CSS в page/service, прямым wallet/network в компоненте и редактором в production dependency graph обязаны падать.
- Components: все варианты, повторный mount/update/dispose, одновременные экземпляры, locale/viewport/theme update, focus/scroll, прерывание FX.
- Visual: настоящие данные через fixtures; screenshot diff по принятым эталонам и покадровые проверки motion. Допуск GPU-шума ограничить явно, не превращать в игнорирование крупных изменений. Новые baseline не принимать автоматически ради зелёного теста.
- Integration: матч -> результат -> сундук -> предмет -> экипировка -> матч; Академия -> репетиция -> попытка -> проверка; nested pause/settings/diagnostics; reward error/retry; reload/Back/background/GPU recovery. Проверять реальные компоненты и построенный HTML, не подставные route-заглушки.
- Roundtrip: изменить цвет, типографику, радиус и параметр сцены в мастерской; сохранить; перезапустить; собрать; сравнить вид и hash в мастерской/оболочке/iframe. Несохранённый draft намеренно не влияет на production.
- Performance: фиксированный сценарий и версия устройства; 30 секунд взаимодействия/FX и повторные циклы навигации, сбор метрик после GC, отсутствие накопления ресурсов. Обзорная доска не запускает 28 игровых движков.

- Existing commands: `python3 source/build.py`; `node --test source/tests/*.test.cjs`; из `source/game` выполнить `npm test`, `npm run test:interface`, `npm run test:academy`, `npm run test:diagnostics`, `npm run test:missshots` и соответствующий browser gameplay suite. Новые workshop/compiler/architecture проверки включить в обычные команды, не оставлять факультативными.
- В production нет доступа к UI-kit editor или визуальным демосценариям по скрытому query-параметру. Действующие legacy-ссылки сохраняют предусмотренную нормализацию; будущие сервисы не включаются этим проектом.

## Финальные Условия

Готовность требует одновременно: подтверждённого визуального уровня, полного общего источника, сохранения/сборки без расхождения, нулевых обходов библиотеки после миграции, функционального паритета и доказательств проверок. Новое удаление выразительности ради упрощения реализации, непроверенная сохранность прогресса или неполученная визуальная приёмка блокируют завершение независимо от числа зелёных тестов.
