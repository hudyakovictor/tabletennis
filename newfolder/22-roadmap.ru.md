**Главные «дыры», найденные при инвентаризации** (это и есть материал плана):

1. **`GET /api/admin/legal` не вызывается из интерфейса.** Юридические документы, реестр DPA с провайдерами, возрастные гейты по регионам, статистика согласий и **запросы субъектов ПДн** (`privacy_requests` с 30-дневным SLA) доступны только через curl. ТЗ `16-legal-player-agreements.md` требует операторского контура, а не API.
2. **Бэкап и retention без кнопок.** `POST /system/backup` и `POST /system/retention` есть, но в SPA на них ничего не ссылается; в планировщике **нет задачи бэкапа** — то есть DR существует как ручной curl и как runbook.
3. **Сессия не продлевается.** `POST /auth/refresh` реализован и не вызывается: через 12 часов оператор выкидывается посреди работы без предупреждения и без сохранения deep-link.
4. **Три API без формы:** `POST /feedback`, `POST /patches`, `POST /liveops/events` — конвейер фидбека, патчей и календарь LiveOps только читаются, но не создаются из UI.
5. **Повторные падения задач планировщика никого не будят** — есть backoff и `consecutive_failures`, но нет эскалации в инцидент/уведомление.
6. **Нет машиночитаемого контракта.** Документ 19 хорош для человека, но новый клиент захочет `openapi.json` и JSON Schema телеметрии, сгенерированные из кода (иначе документ и код разойдутся, как уже было с ключами зон).

## 1. Принципы очерёдности

1. **Сначала то, что «уже обещано»** — экраны для существующего API и защита данных. Это дешёвые победы с высоким риском доверия.
2. **Потом эксплуатация** — бэкап, восстановление, эскалация, нагрузочный профиль. CRM без DR-учений — демо.
3. **Только затем клиент.** Пока не будет машинного контракта и симулятора клиента, переписывание клиента упрётся в «а как должен вести себя сервер при 429 в середине пакета?».
4. **Никаких новых зависимостей.** Всё, что нужно, уже есть в Node 22 (`node:sqlite`, `node:crypto`, `node:test`); jsdom остаётся единственным dev-пакетом.
5. **Каждая задача закрывается тест-гейтом.** Задача без падающего теста — не задача, а намерение.

Обозначения объёма: **S** ≤ 2 ч · **M** 2–6 ч · **L** 1–2 дня.

## 2. Фаза A — Юридический и эксплуатационный контур (P0, 1 спринт)

### A1. Экран «Право и приватность» (S/M) — вкладка в «Управление»
**Что:** вкладка `legal` на экране Governance, питается `GET /api/admin/legal`.
**Содержимое:**
- 4 юридических документа (ToS / Privacy / EULA / Cookie) с версией, языком и датой — просмотр полного текста в drawer;
- реестр DPA по провайдерам: провайдер, статус договора, регион, zero-retention, дата;
- возрастные гейты по регионам (US 13 / EU 16 / RU 14 / DEFAULT 13) с пояснением, что происходит при отказе;
- статистика согласий по регионам (всего, несовершеннолетние с согласием опекуна, opt-in аналитика/маркетинг);
- **очередь запросов субъектов ПДн**: тип (экспорт/удаление), игрок, дата, SLA 30 дней с прогресс-баром, кнопки «Выгрузить», «Удалить ПДн», «Отклонить с причиной».
**Почему:** это единственный блок ТЗ, к которому сейчас нет ни одного экрана; запрос субъекта ПДн по 152-ФЗ — юридический срок, а не «фича».
**Готово, когда:** вкладка рендерится без ошибок, действия пишут в аудит (`legal.privacy_request.exported/erased/rejected`), в контрактный тест попадает проверка «каждый админ-эндпоинт либо вызывается из SPA, либо в allow-list с обоснованием».

### A2. Бэкапы и retention как операция, а не как runbook (M)
**Что:**
- кнопки «Сделать бэкап» и «Запустить retention» в «Настройки → Диагностика» с подтверждением и тостом о результате;
- **dry-run retention**: сначала показываем, сколько строк будет удалено по каждому правилу (90/180/365), потом применяем — сейчас политика необратима и «на глаз»;
- задача планировщика `db_backup` (ночь), ротация: держим N последних + один в месяц, старые удаляем;
- проверка восстановления: открыть бэкап в режиме read-only, `PRAGMA integrity_check`, сравнить `head_hash` аудита с текущим, отчёт в диагностике.
**Готово, когда:** `POST /system/backup` вызывается из UI, появилась задача `db_backup` с записью в `scheduler_jobs`, есть тест «бэкап создаётся, целостен и содержит тот же head_hash», а retention имеет тест «dry-run не удаляет».

### A3. Живая сессия оператора (S)
**Что:** вызов `POST /auth/refresh` по расписанию (за 25 % до истечения и при `visibilitychange`/возврате фокуса), баннер «сессия истекает через N минут», после `401` — экран входа с сохранением hash и восстановлением того же экрана после логина.
**Готово, когда:** UI-тест «сессия продлена без перезагрузки» и «после истечения возвращаемся на тот же deep-link»; в `API` нет ни одного 401 в happy-path прогона.

### A4. Формы конвейера LiveOps (S)
**Что:** создание фидбека (`POST /feedback`), патча (`POST /patches`) и события календаря (`POST /liveops/events`) прямо из вкладки «Фидбек» и «Календарь».
**Готово, когда:** три POST-а вызываются из UI, в контрактном тесте нет «эндпоинтов без UI», кроме осознанного allow-list (telegram webhook, refresh).

## 3. Фаза B — Архитектура, устойчивость, безопасность (P1, 1–2 спринта)

### B1. Разделить `adminRoutes.js` (2 165 строк) на доменные роутеры (L)
**Что:** `routes/admin/{auth,zones,hitl,director,fraud,players,liveops,system}.js` по образцу `platformRoutes.js` (возврат `null` = «не мой маршрут»), реестр роутеров в одном месте.
**Зачем:** сейчас любой конфликт правок — это конфликт в 2-тысячном файле; плюс появляется возможность статически проверить таблицу маршрутов.
**Готово, когда:** **новый тест** «нет двух обработчиков на один `метод+путь`» проходит (сейчас такой проверки нет — тень одного маршрута другим обнаруживается только вручную), размер каждого файла ≤ 600 строк, все 32 теста зелёные.

### B2. Версионирование схемы вместо списка в коде (M)
**Что:** таблица `schema_migrations(version, name, applied_at)`, миграции — упорядоченный массив `{version, name, up(db)}`, `npm run db:status` печатает применённые/ожидающие. Текущий `COLUMN_MIGRATIONS` переносится как baseline `v1`.
**Готово, когда:** повторное открытие БД идемпотентно, `db:status` на свежей БД показывает все применённые версии, тест «миграция поверх старой БД не теряет данные».

### B3. Вход: 2FA и лимиты по аккаунту, а не только по IP (M/L)
**Что:** TOTP-секрет для роли `admin` (генерация QR-строки без зависимостей, `otpauth://`), 10 резервных кодов (хешируются), обязательный шаг после пароля; троттлинг **по аккаунту** в дополнение к IP (сейчас 5 попыток на IP — атака с ботнета обходит), уведомление владельцу о новом IP-хеше входа.
**Готово, когда:** вход без кода → 401 `TOTP_REQUIRED`, неверный код → 401 с задержкой, резервный код одноразовый, всё в аудите; тест «2FA нельзя обойти bearer-токеном, выданным до включения».

### B4. Связать silences, SLO и публикацию правил (S)
**Что:** (a) аномалия под активным silence не создаёт уведомление/инцидент (сейчас silence только отображается); (b) публикация `MATCH_RULES` блокируется при `breached` по SLO доступности — с явным override владельца и обоснованием.
**Готово, когда:** два теста: «silence подавляет уведомление, но не скрывает метрику» и «публикация при breached → 409 без override, 200 с override + аудит».

### B5. Канарейка prompt-injection в CI (S)
**Что:** корпус из ~30 атак (инструкции в данных, гомоглифы, base64, «забудь предыдущие инструкции», подделка JSON-схемы), прогон через `promptGuard` + `jsonSchema`, ожидание: санитайз или карантин, ноль исполнения.
**Готово, когда:** `npm run test:security` в `test:all`, каждая атака — отдельный кейс с ожидаемым исходом.

### B6. Метрики realtime и калибровка антифрода (M)
**Что:** счётчики WS (выдано тикетов / подключений / отказов / reconnect / разрывов по причине), в наблюдаемости — панель realtime; региональная калибровка `reactionMs` (медиана и p95 по регионам, порог подозрения — от региональной базовой линии, а не глобальной).
**Готово, когда:** значения видны в `/observability`, есть тест «reconnect инкрементит счётчик», фрод-детектор использует региональную базовую линию (тест с двумя регионами).

### B7. Эскалация падений планировщика (S)
**Что:** 3 подряд `failed` → инцидент `scheduler_job_down` + уведомление + запись в аудит; восстановление закрывает инцидент. Плюс «мёртвая рука»: если задача не запускалась дольше 2× интервала — тоже инцидент.
**Готово, когда:** тест «три падения → инцидент создан один раз, четвёртое не дублирует».

### B8. Нагрузочный профиль (M)
**Что:** `tools/load.mjs` без зависимостей: 50 параллельных админ-чтений + 20 стартов сессий/с + 200 событий телеметрии/с + 50 WS-подключений в течение 30 с; отчёт p50/p95/p99, ошибки, RSS. Отдельный скрипт `npm run test:load` (не в CI по умолчанию).
**Готово, когда:** базовый прогон фиксируется в документе (p95 и потолок), регресс > 20 % считается провалом.

## 4. Фаза C — Машиночитаемый контракт и подготовка нового клиента (P1, следующий крупный шаг)

### C1. Генерация `openapi.json` + JSON Schema из кода (L)
**Что:** из таблицы маршрутов (после B1) генерируем OpenAPI 3.1 для `/api/client/v1/*` и `/api/admin/*` (группы, права, коды ошибок), плюс `client-telemetry.schema.json`, `match-rules.schema.json`, `notifications.schema.json`. Раздача: `GET /api/client/v1/openapi.json`, файл кладётся в репозиторий и **диффится в CI** (устаревший файл = красный тест).
**Зачем:** ровно та же болезнь, что была с `/zones/:zone/config` — документ обещает, код не делает; генерация убирает класс ошибок целиком.
**Готово, когда:** тест «openapi соответствует маршрутам», документ 19 ссылается на схему, а не пересказывает её.

### C2. Симулятор клиента как исполняемая спецификация (M/L)
**Что:** `tools/client-sim.mjs`: bootstrap → telegram auth (тестовая подпись) → consent → session/start → ws/ticket → WS welcome → 3 пакета телеметрии (с дублем `clientEventId`, с `429`, с `503` в техработы) → session-end → тикет поддержки → dismiss уведомления. Проверяет не только 200, но и поведение при отказах: `Retry-After`, повтор с тем же ключом, реконнект по affinity.
**Зачем:** новый клиент получит готовый эталон последовательности и ожиданий, а мы — регрессионный тест стыка.
**Готово, когда:** `npm run test:client` зелёный, сценарий описан в документе 19 как «reference flow».

### C3. Режим мока для параллельной разработки клиента (S)
**Что:** `CLIENT_MOCK_MODE=1` — детерминированные ответы (фиксированные `serverTimeUtc`, предсказуемый `abVariant`, принудительные ошибки по заголовку `X-Mock-Fault: 503|429|timeout`), чтобы фронтенд мог разрабатываться без сервера и без «повезёт/не повезёт».
**Готово, когда:** режим документирован, покрыт тестом и не влияет на прод-путь (`env !== 'production'`).

### C4. Бюджет задержек клиентского контура (S)
**Что:** в нагрузочном профиле отдельные SLO: p95 `/bootstrap` ≤ 120 мс, `/session/start` ≤ 150 мс, `/telemetry/inputs` ≤ 80 мс, `/ws/ticket` ≤ 60 мс на локальной машине; регресс ловится `test:load`.
**Готово, когда:** цифры зафиксированы в документе и в отчёте, пороги в скрипте.

## 7. Definition of Done (одинаково для всех задач)

1. Код + миграция (если нужна) + запись в аудит для любого действия человека.
2. Тест, который **падает без изменения** (проверено мутацией), и он входит в `npm run test:all`.
3. Документация: обновлены `19` (если клиентский контракт), `20` (если экран/кнопка), `README` (если команда/файл), плюс строка в `21` как «Дополнение» к профильному разбору — не 31-й анализ.
4. Ручная проверка на живом превью: сценарий из DoD проходит в браузере, а не только в jsdom.
5. Ни одной новой runtime-зависимости; если без неё нельзя — обоснование в тексте задачи.

## 9. Что сознательно НЕ делаем

- **Не трогаем `source/` и `play/`** — демо-клиент будет переписан; любые правки там выброшены.
- **Не добавляем фреймворки и сборщики** (React/Vue/Vite): текущая архитектура на модулях ES + CSP `script-src 'self'` покрывает потребности и не тянет supply-chain риск.
- **Не переходим на Postgres** в этой итерации: SQLite-схема с WAL даёт нужные гарантии на этом объёме, а `postgres-schema.sql` остаётся миграционным путём для продакшена.
- **Не автоматизируем сам бэкап-рестор до Фазы A2** — сначала dry-run, потом автоматика; иначе однажды автоматика восстановит не то.
